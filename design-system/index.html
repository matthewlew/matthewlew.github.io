Cards & Surfaces

Card components use the semantic tokens internally so they react flawlessly to theme and mode changes.

How Emphasis Inheritance Works

By default, buttons and text simply inherit the emphasis of their parent card. They automatically pull from var(--text), var(--border), and var(--background).

Bespoke Overrides

To override the emphasis for a specific element (like making a single button or badge pop), simply drop an .emph-* class directly onto it. Because of the One-Token architecture, the browser locally re-resolves the variables for just that node without breaking the parent surface.

NewSurfaces & Breakpoints

Emphasis answers how loud is this object. It never answered how deep is this plane — a card and the page behind it can both be emph-plain and still must not be the same colour. Five depth roles, applied with .surface-*, filled by the theme.

The stack — switch to Roadtrip above to see a dark-native theme use all five
surface-page
surface-sunken
surface-base
surface-raised
surface-overlay

In light the top three collapse to one value: on oat paper a brighter card reads as a hole, not as nearer, so elevation is carried by shadow. In dark the bottom two collapse, because nothing sits below the darkest step — and shadow is invisible there, so elevation has to be lightness. That is why a dark-native product needs five distinct surfaces and the portfolio needs two.

Breakpoints — named for what the layout gains, not for a device
TokenValueWhat changes
--bp-sm480pxOne column, thumb reach, no persistent chrome.
--bp-md768pxTwo columns fit, or a rail plus content.
--bp-lg1024pxA persistent sidebar stops costing content width.
--bp-xl1440pxLine length, not space, becomes the constraint.
--bp-short520px tallNothing may assume vertical room.

Width decides the column count; height decides whether anything may assume vertical room. A phone in landscape is ~900px wide and ~400px tall — every width-only breakpoint files it as a tablet, which is exactly how centred modals and full-height drawers end up with their buttons below an unscrollable fold. Rotate your phone: this line is visible in portrait and hidden in landscape. Tall enoughShort viewport — vertical room is not assumed

Gotcha: a custom property cannot be read inside a media query. @media (min-width: var(--bp-md)) does not error — the block is silently dropped. The @media rules still spell the number; the token is the record of what it means, and the value JS reads so the two cannot drift.

Guidance

The rules of the system. Follow these to ensure LDS remains scalable, machine-readable, and robust across every project.

1. Token Hierarchy & Inheritance

The One-Token architecture relies on natural cascading. Do not break it.

✓ Do

  • Inherit by defaultLet components inherit their environment (var(--text), var(--background)) so they adapt contextually.
  • Use explicit overridesAlways use explicit .emph-* classes to drive bespoke component color changes.

✕ Don't

  • No raw hex valuesNever use raw hex values or bypass the One-Token architecture.
  • No bespoke color classesNever create bespoke CSS classes (like --btn-primary-bg) to color a component.

2. Color & Surfaces

How to apply emphasis and style across UI components.

✓ Do

  • Reserve accent colorsReserve signature accent colors for active states, labels, or a single rule line. Scarcity is the point.
  • Apply emphasis directlyUse .emph-* classes directly on HTML elements to create overrides without breaking the parent surface.

✕ Don't

  • Don't flood with strong emphasisDon't flood the UI with .emph-strong. If it feels loud, there's too much.
  • No arbitrary shadowsDon't add shadows or gradients-as-decoration. It breaks the structural language.

3. Components & Layout

Rules for spacing, shapes, and structural hierarchy.

✓ Do

  • Use 1px hairlinesSeparate UI sections with 1px hairlines (var(--border)). Structure carries hierarchy.
  • Use semantic radiiAlways use --radius-sm, --radius, --radius-lg, or --pill.
  • Cards for rich mediaUse Cards only for standalone content with rich media and multiple actions. Lists for scannable content.

✕ Don't

  • No hardcoded radiiNever hardcode pixel values for border-radius. These shift dynamically based on the active brand theme.
  • Don't mix cards and listsDon't mix cards and list items for the same content type. Keep structural patterns consistent.
  • Don't stack strong CTAsDon't put two .emph-strong buttons next to each other. One primary action per view context.
